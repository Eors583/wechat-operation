# 微信公众号文章排版学习智能体技术方案 v1.0

> 文档状态：方案设计，待评审  
> 适用范围：微信公众号文章链接解析、排版模板提取、模板延展、用户排版偏好学习  
> 基线文档：`docs/微信公众号AI运营助手_完整技术设计文档_v3.0.md`  
> 设计原则：本文扩展 V3.0 的 `layout_extraction` 能力，不改变“模型不直接生成最终微信 HTML、Render 不可变、发布前必须确认”的安全边界。

## 1. 结论摘要

现有排版提取器能读取微信公众号文章 HTML，并按标签、字号、字重和内联样式推断标题、正文、引用等模块。这种实现适合作为可靠的基础解析器，但不能独立完成高质量版式理解，主要原因是：

- DOM 标签不等于内容语义。大量公众号文章使用嵌套 `section`、`p`、`span` 模拟卡片、标题序号和装饰结构。
- 内联 CSS 只能说明局部样式，不能完整表达视觉层级、组合关系、留白节奏和整篇文章的设计语言。
- 同一模块可能有多个变体，例如一级标题可以交替使用数字徽标、色块标题和分隔线标题；现有“一种模块对应一组 StyleToken”无法表达。
- 当前规则主要选择高频值，能提取“常见字号和颜色”，但难以学习“为什么这一组元素共同组成一个标题组件”。
- 纯截图识别同样不够：截图能看见布局，却难以可靠获得文字角色、精确尺寸、链接与图片语义。

因此，本方案不废弃 HTML/DOM，而是把它从“最终判断者”降级为智能体的一个传感器。推荐架构是：

```text
公众号链接
  → 安全抓取与受控浏览器渲染
  → 页面截图 + 元素空间树 + 受限计算样式 + 文本角色线索
  → 排版学习智能体（多模态理解、范例检索、候选生成）
  → Layout Blueprint 排版蓝图
  → 确定性校验、编译、微信兼容检查和视觉回归
  → 用户选择/修改/确认
  → 偏好画像与训练样本闭环
```

智能体负责“理解、归纳、组合和生成候选”，确定性服务负责“输入安全、Schema 校验、样式白名单、HTML 编译、版本冻结和发布一致性”。智能体永远不能直接保存任意 HTML/CSS，也不能直接调用微信草稿或发布接口。

建议先实现兼容现有 StyleToken 的混合智能提取 MVP，再升级到能表达模块变体的 `Layout Blueprint v2`。在没有足够高质量用户反馈前，不做在线微调；首版的“学习”使用检索增强、账号画像和用户确认后的增量统计完成。

## 2. 现状审查

### 2.1 当前链路

当前仓库中的排版提取链路如下：

```text
LayoutTemplateEditor.vue
  → POST /api/v1/layout-templates/extract
  → 校验 mp.weixin.qq.com HTTPS 链接
  → 冻结 layout_extraction 模型路由
  → 创建 LayoutTemplate、JobRecord 和 Outbox
  → WeChatPublicLayoutExtractionProvider.extract()
  → HTMLParser 提取正文文本和继承的内联样式
  → 启发式归类 title/heading/body/quote/list/caption
  → validate_style_tokens()
  → 创建不可变 LayoutTemplateVersion
  → 用户手工调整并保存新版本
  → create_render() 编译为白名单微信 HTML
```

现有实现已经具备以下可复用基础：

| 能力 | 现有位置 | 评估 |
|---|---|---|
| 微信公开文章 URL 限制和守卫页识别 | `app/wechat_public_layout.py`、`domains/layout.py` | 应保留并加强 |
| `layout_extraction` 逻辑用途路由及冻结快照 | `app/model_gateway.py`、`api/user.py` | 已有接入点，但模型尚未实际参与提取 |
| StyleToken 白名单和范围校验 | `domains/layout.py`、`api/contracts.py` | 是智能体输出的第一道安全边界 |
| 模板与模板版本不可变模型 | `models.py` | 可继续承载 MVP 输出 |
| HTTP 排版提取 Provider | `production_providers.py` | 可作为受控浏览器或独立排版服务的扩展边界 |
| 微信兼容 HTML 的确定性渲染 | `domains/layout.py` | 必须保留，不能由模型替换 |
| 前端逐模块调整和预览 | `LayoutTemplateEditor.vue` | 可用于收集用户修正反馈 |

### 2.2 当前实现的关键缺口

1. `process_layout_extraction()` 虽然接收模型、密钥和冻结路由，但只记录 `not_used_deterministic_extraction`，没有真正调用模型。
2. 提取器只读取 HTML 中有限的内联属性，没有受控浏览器的计算样式、真实边界框、层叠结果和页面截图。
3. `_style_tokens()` 依赖字号、字重和文本长度等规则，面对“数字标识 + 标题文字 + 背景装饰”的组合组件时容易误判。
4. `StyleTokenPayload` 每个语义模块只有一份样式，无法表达模块结构、装饰配方、多个变体和变体选择规则。
5. 现有模型 Provider 的通用 `generate()` 主要传入文本化 JSON，上游适配器没有统一的图片输入和强制结构化输出协议，不能直接支撑多模态排版理解。
6. 当前用户编辑结果只形成模板新版本，没有转化为“提取结果与最终确认版本的差异”这一学习信号。
7. 当前接口返回语义更接近同步完成，虽然创建了异步 Job 和 Outbox。引入截图与模型调用后，应真正异步执行并允许查询阶段进度。
8. 请求中的 `save_template` 当前只进入冻结载荷，没有形成明确的“仅预览候选”与“自动保存模板”行为差异。

## 3. 目标与非目标

### 3.1 目标

- 同时理解文章的视觉表现、空间结构、文本语义和可复用样式规律。
- 从一篇参考文章提取一个忠实模板，并可选择生成多个保持设计语言一致但结构不同的候选模板。
- 从用户确认、修改、启停和实际使用行为中学习个人或公众号级排版偏好。
- 输出受控、可解释、可验证、可版本化的排版蓝图，而不是任意 HTML/CSS。
- 继续使用现有模型网关、路由快照、审计、模板版本、Render 和发布确认机制。
- 模型不可用或输出不合法时可安全失败，或者明确降级到现有 DOM 基础提取，不生成伪造成功结果。

### 3.2 非目标

- 不让智能体登录用户微信、创建草稿或发布文章。
- 不复制参考文章的正文、图片、品牌 Logo、二维码或受版权保护的装饰素材。
- 不执行网页脚本中的指令，不将网页文字当作系统提示。
- 首版不训练独立基础模型，不建设多智能体协作集群，也不引入实时在线参数微调。
- 不允许用户或模型向最终 Render 注入任意标签、脚本、事件属性、外链 CSS 或任意 CSS 表达式。

## 4. 核心设计原则

### 4.1 多模态理解，但不抛弃确定性证据

截图负责提供真实视觉结果；元素空间树提供顺序、尺寸、位置和层级；受限计算样式提供精确颜色、字号和间距；文本只提供语义线索。四类信息互相校验，任何一种都不单独决定最终模板。

### 4.2 智能体输出 DSL，不输出最终 HTML

智能体只能输出 `Layout Blueprint`。蓝图中的模块、配方、属性和取值均来自受控目录。后端将其校验并编译为微信兼容 HTML。这样可以把模型的开放推理限制在安全、可测试的表示层内。

### 4.3 学习来自用户确认，不来自未经确认的参考页

外部文章只能产生候选模板。只有以下信号可提高用户偏好权重：

- 用户明确选择某个候选；
- 用户保存修改后的模板；
- 模板被启用并用于生成 Render；
- 用户确认保存到公众号草稿或确认发布；
- 用户显式评价“喜欢/不喜欢”或删除模板。

AI 初稿、单次浏览、未保存拖动和外部文章本身不能直接写入长期偏好。

### 4.4 先做运行时学习，再考虑模型训练

首版使用“检索相似优秀模板 + 账号排版画像 + 当前文章约束”进行上下文学习。只有积累足够多经用户确认、可匿名化、通过质量检查的数据后，才评估离线微调或偏好优化。这样可以避免小样本过拟合、错误反馈污染和训练基础设施过早膨胀。

## 5. 总体架构

### 5.1 逻辑组件

| 组件 | 职责 | 是否允许非确定性 |
|---|---|---:|
| 安全抓取器 | URL、DNS、重定向、响应类型、体积、超时和守卫页检查 | 否 |
| 页面观察器 | 在固定移动端视口渲染页面，生成截图、元素边界框、受限计算样式和资源统计 | 否 |
| 内容角色预标注器 | 用已有规则产生标题、正文、引用等弱标签，不直接形成最终模板 | 否 |
| 排版范例检索器 | 按账号、行业、内容结构和视觉特征检索已确认范例 | 排序可近似 |
| 排版学习智能体 | 综合截图、空间树、弱标签和范例，输出一至多个排版蓝图 | 是 |
| 蓝图验证器 | JSON Schema、白名单、数值范围、引用完整性、复杂度和兼容性检查 | 否 |
| 蓝图编译器 | 将蓝图编译为白名单内联 HTML 和 StyleToken v1 兼容视图 | 否 |
| 视觉评测器 | 渲染样例文章，检查溢出、截断、对比度、移动端几何和视觉相似度 | 否/模型仅作辅助评分 |
| 学习闭环 | 将确认、编辑差异和使用结果更新为账号画像与训练样本 | 否 |

### 5.2 部署建议

MVP 不新增独立微服务。继续由 `platform-backend` 负责领域编排，在 Celery 的排版任务中调用受控 Chromium 页面观察器和模型网关。浏览器依赖放入专用 Worker 镜像或现有 parser Worker 的可选层，API 进程不启动浏览器。

现有 `LAYOUT_PROVIDER_MODE=http` 继续保留：当生产环境需要更严格隔离或浏览器负载独立扩缩容时，页面观察器可以迁移为签名 HTTP 服务，但业务事实、模型路由、用户所有权、模板版本和审计仍由 `platform-backend` 掌握。

只有当以下任一条件出现时，才拆分独立 `layout-observer` 服务：

- Chromium 内存或并发显著干扰 AI/文件 Worker；
- 需要不同的网络出口与沙箱策略；
- 页面渲染任务需要独立弹性扩容；
- 浏览器安全补丁需要独立发布节奏。

## 6. 页面观察：智能体到底“看见”什么

### 6.1 固定渲染环境

页面观察器使用接近微信公众号阅读区的固定环境：

- 视口宽度以 375 CSS px 为主，另以 414 CSS px 做几何复核；
- 固定设备像素比、字体候选集、语言和时区；
- 禁止下载、弹窗、摄像头、麦克风、地理位置、剪贴板和持久化 Cookie；
- 默认阻止正文以外的第三方脚本、追踪和不必要网络请求；
- 页面达到正文稳定条件或超时后截取完整正文和分段截图；
- 每个网络跳转都重新进行域名和私网地址检查，防止 DNS Rebinding 与重定向绕过。

### 6.2 Layout Observation v1

观察结果不保存完整原始 HTML，而是保存最小、可复现、可审计的结构化证据：

```json
{
  "schema_version": 1,
  "source": {
    "url_hash": "sha256:...",
    "final_host": "mp.weixin.qq.com",
    "title": "示例标题",
    "account_name": "示例公众号",
    "captured_at": "2026-09-03T00:00:00Z"
  },
  "viewport": {"width": 375, "height": 812, "device_scale_factor": 2},
  "artifacts": {
    "full_screenshot_key": "layout-observations/.../full.webp",
    "segment_screenshot_keys": ["layout-observations/.../segment-01.webp"]
  },
  "blocks": [
    {
      "id": "b17",
      "parent_id": "b12",
      "order": 17,
      "tag_hint": "section",
      "text_excerpt": "01 品牌增长",
      "role_hint": "heading1",
      "bbox": {"x": 24, "y": 830, "width": 327, "height": 58},
      "style": {
        "font_size": 20,
        "font_weight": 700,
        "line_height": 1.5,
        "color": "#1f2937",
        "background": "#ecfdf5",
        "text_align": "left",
        "margin_top": 24,
        "margin_bottom": 14,
        "padding": [8, 12, 8, 12],
        "border": {"left": "4px solid #059669"}
      }
    }
  ],
  "statistics": {
    "text_block_count": 64,
    "image_count": 7,
    "dominant_colors": ["#059669", "#1f2937", "#f3f4f6"]
  },
  "content_hash": "sha256:..."
}
```

约束如下：

- `text_excerpt` 只保留角色判断所需短文本，设置单块和总量上限；模型输入中明确标记为不可信数据。
- `style` 只包含白名单计算样式，不包含表达式、URL、动画、定位脚本或自定义变量。
- 截图进入私有对象存储，使用短时签名读取；数据库只保存对象键、哈希、尺寸和版本。
- 图片本身只用于判断占位、比例、圆角和说明文字关系，不作为模板素材复制。
- 对重复装饰节点进行合并，限制最大节点数；超限时按视觉显著性和模块覆盖抽样。

### 6.3 DOM 规则的新角色

现有 `_style_tokens()` 不再是智能结果的唯一来源，而是提供三种能力：

1. 生成弱标签和基础候选，减少模型从零识别的成本；
2. 当模型结果与精确计算样式冲突时提供数值校正证据；
3. 模型不可用时提供明确标记的“基础提取”降级结果。

降级结果必须在 `source_snapshot.extraction_mode` 中记录为 `deterministic_fallback`，前端显示“已使用基础提取，可手动调整”，不能伪装成智能学习结果。

## 7. 排版学习智能体

### 7.1 单一专用智能体，而不是智能体群

首版只需要一个“排版学习智能体”。它是后台专用能力，不作为新的用户对话智能体出现，因此不改变 V3.0“用户只面对一个内容创作智能体”的产品约束。它运行在现有 Model Gateway 的 `layout_extraction` 用途中，使用具备图片理解和结构化输出能力的部署。安全抓取、Schema 校验、编译和评分都是确定性工具，不再各自包装成独立智能体。

这样能避免多智能体间状态同步、重复调用、成本不可控和难以复现，同时已经足以完成版式理解和候选生成。

### 7.2 智能体职责

智能体只做以下工作：

1. 根据截图和空间树识别文章的视觉层级与语义模块；
2. 归纳颜色系统、字体层级、间距节奏、对齐方式和装饰母题；
3. 识别哪些元素应组合为一个可复用模块配方；
4. 将来源版式映射到平台的安全配方目录；
5. 根据模式输出一个忠实候选，或多个有差异但同源的候选；
6. 为每个模块返回置信度和证据块 ID，便于调试和质量门禁；
7. 在给定账号画像时优先满足已确认偏好，但不能覆盖用户本次明确选择。

智能体无权抓取任意 URL、执行 JavaScript、写数据库、调用微信、创建文件或绕过蓝图验证器。

### 7.3 输入组成

一次运行的冻结输入包含：

| 输入 | 说明 |
|---|---|
| 操作协议 | 平台安全规则、任务目标、模式和输出 Schema |
| Layout Observation | 截图、空间树、计算样式、弱标签和统计 |
| Recipe Catalog | 当前允许使用的模块配方及参数范围 |
| StyleToken 约束 | 现有模块和安全属性白名单 |
| 账号排版画像 | 仅来自已确认行为，带版本和置信度 |
| 检索范例 | 最多若干个相似、已确认、已匿名化的蓝图摘要 |
| 用户本轮要求 | 例如“忠实提取”“更简洁”“生成三个差异明显版本” |
| 冻结版本 | 模型路由、提示词、Schema、配方目录、观察器版本 |

网页正文、截图内文字、账号名称、图片文字、历史范例说明均放在不可信上下文区。即使页面中出现“忽略系统规则”等内容，也只能被视为待排版文本。

### 7.4 两阶段推理

智能体在一次业务任务内执行最多两次模型调用：

1. **分析调用**：输出版式 DNA、模块识别、证据映射和不确定项。
2. **生成调用**：基于分析结果输出一个或多个符合 Schema 的蓝图候选。

如果模型支持稳定的强结构化输出，可在评测证明质量不下降后合并为一次调用。输出只允许一次受限结构修复；修复后仍不合法则失败或降级，不进行无限自我反思和重试。

### 7.5 输出置信度

置信度不是模型一句主观评分，而由以下信号组合计算：

- 模型给出的角色置信度；
- 视觉证据与 DOM 弱标签是否一致；
- 相同角色在文章中是否重复出现；
- 蓝图编译后的视觉特征与来源观察是否接近；
- 是否经过结构修复、属性裁剪或配方替换；
- 是否命中高置信度账号偏好。

置信度用于排序和提示用户，不用于绕过安全校验。低置信度仍必须生成合法、安全的蓝图，或者停止并提示需要手动调整。

## 8. Layout Blueprint v2

### 8.1 为什么必须升级表示层

现有 StyleToken 能描述“一级标题字号 22、绿色、左对齐”，但不能描述“左侧数字徽标 + 右侧标题 + 下方短横线”这种组合结构。若只让模型继续输出 StyleToken，模型再聪明也只能生成颜色和字号的排列组合，多样性上限很低。

`Layout Blueprint v2` 在 StyleToken 之上增加“安全模块配方”和“有限变体选择”，同时保留 v1 兼容投影。

### 8.2 蓝图示例

```json
{
  "schema_version": 2,
  "name": "克制绿色编辑风",
  "style_tags": ["editorial", "clean", "green-accent"],
  "design_tokens": {
    "palette": {
      "text": "#1f2937",
      "muted": "#6b7280",
      "accent": "#059669",
      "surface": "#ecfdf5"
    },
```

### 8.3 安全配方目录

首批配方应控制在真正需要的最小集合：

| 模块 | 建议配方 |
|---|---|
| 标题 | `plain_title`、`centered_title`、`title_with_rule` |
| 一级/二级标题 | `plain_heading`、`left_bar_title`、`number_badge_title`、`filled_label_title`、`underlined_title` |
| 导语/重点 | `plain_text`、`accent_card`、`top_bottom_rule` |
| 引用 | `left_bar_quote`、`soft_card_quote`、`quote_mark_card` |
| 列表 | `plain_list`、`numbered_list`、`accent_bullet_list` |
| 图片说明 | `plain_caption`、`centered_caption` |
| 分隔线 | `solid_rule`、`short_accent_rule`、`dot_rule` |

每个配方由后端代码维护固定标签结构和允许参数，不允许模型提供模板字符串。只有两个不同来源模板确实需要同一种新结构时，才新增配方；不要为单篇文章创建一次性配方。

### 8.4 与 StyleToken v1 的兼容

- 每个 v2 模块必须有一个默认变体。
- 编译器可把默认变体的基础样式投影为现有 `style_tokens`，供当前前端编辑器和旧 Render 使用。
- MVP 阶段智能体直接输出 v1 StyleToken；v2 上线后，同一个模板版本同时保存 `blueprint` 和 `style_tokens_projection`。
- v1 模板继续正常渲染；只有 v2 模板启用配方编译。
- 模板版本冻结 `blueprint_schema_version` 和 `recipe_catalog_version`，避免配方升级改变历史 Render。

## 9. 多样化输出策略

多样化不能等同于随机换颜色。候选之间至少应在两个设计维度上有可感知差异，同时保持同一参考文章或账号的设计 DNA。

### 9.1 三种运行模式

| 模式 | 输出 | 使用场景 |
|---|---|---|
| `faithful` 忠实提取 | 1 个最接近来源的候选 | 用户明确要复刻参考版式 |
| `variations` 智能延展 | 默认 3 个候选 | 从同一风格生成不同模块组合 |
| `account_profile` 账号学习 | 1—3 个候选 | 按该公众号已确认的长期偏好排版 |

忠实提取是现有链接入口的默认行为，不能为了展示“AI 多样性”而擅自偏离参考文章。用户主动选择智能延展后，才生成多个候选。

### 9.2 多样性约束

候选生成时固定以下不变量：

- 正文可读性和字号下限；
- 主色与中性色之间的关系；
- 标题层级顺序；
- 微信兼容性和安全属性范围；
- 用户明确锁定的品牌色、对齐和正文密度。

允许变化的维度包括：

- 标题配方；
- 一级标题和二级标题的组合关系；
- 重点段落与引用的容器形式；
- 分隔线、序号和列表标记；
- 留白密度；
- 强调色使用比例。

后端对候选计算特征距离。如果两个候选只有微小色差或数值差异，则视为重复，保留得分更高的一个并要求智能体补充一次；仍重复时返回较少候选，不无限重试。

## 10. 学习闭环

### 10.1 三层学习机制

#### 第一层：单次文章内学习

智能体从当前页面的重复模块中归纳设计规律，例如三个一级标题都使用相同的左边框和间距。这是一次运行内的上下文归纳，不持久修改模型。

#### 第二层：用户/公众号画像学习

系统根据已确认行为维护结构化画像：

```json
{
  "scope": {"owner_id": "...", "official_account_id": "..."},
  "version": 7,
  "sample_count": 18,
  "preferences": {
    "body_font_size": {"value": 16, "confidence": 0.93},
    "body_line_height": {"value": 1.8, "confidence": 0.88},
    "heading_alignment": {"value": "left", "confidence": 0.81},
    "preferred_recipes": ["left_bar_title", "soft_card_quote"],
    "avoided_recipes": ["filled_label_title"],
    "accent_palette": ["#0a8f52", "#065f46"],
    "density": "comfortable"
  }
}
```

画像更新规则：

- 显式选择、保存和确认的权重高于隐式使用；
- 单次行为只形成候选偏好，重复行为或显式确认后才提高置信度；
- 用户本轮明确要求始终高于画像；
- 通用用户画像和公众号画像分开，公众号画像优先；
- 用户可查看、重置或关闭排版学习；
- 删除模板或账号时按数据保留规则删除或解除关联画像。

#### 第三层：离线模型优化

只有在高质量数据达到可用规模并通过隐私审查后，才构造离线数据集：

- 正样本：观察输入 → 用户最终确认蓝图；
- 偏好对：被选择候选 > 被拒绝候选；
- 修正对：智能体初始蓝图 → 用户最终保存蓝图；
- 失败样本：Schema 修复失败、视觉溢出、微信兼容失败和明显误分类。

建议在至少积累约 1,000 个经确认、去重、覆盖多个版式类别的样本，并证明提示词 + 检索画像已遇到稳定瓶颈后，再评估 SFT 或偏好优化。上线条件不是样本数量本身，而是新模型在冻结评测集上显著优于当前版本，并且安全、兼容和成本指标不退化。

### 10.2 反馈事件

首版不记录每一次滑块拖动，只在有业务意义的节点记录快照差异：

| 事件 | 学习价值 | 是否进入长期画像 |
|---|---:|---:|
| `candidate_viewed` | 低 | 否 |
| `candidate_selected` | 高 | 是，先作为候选 |
| `template_saved_after_edit` | 高 | 是，记录字段级差异 |
| `template_enabled` | 中 | 是 |
| `render_confirmed` | 高 | 是 |
| `wechat_draft_succeeded` | 中 | 是 |
| `publish_succeeded` | 高 | 是 |
| `template_disabled` | 中等负反馈 | 是 |
| `template_deleted` | 高负反馈但需区分清理行为 | 进入样本前需确认语境 |
| `explicit_like/dislike` | 最高 | 是 |

同一 Render 的草稿成功和发布成功不能重复放大同一偏好，应按业务链路去重。

## 11. 数据模型演进

## 12. API 演进

### 12.1 保持现有调用兼容

现有接口继续保留：

```http
POST /api/v1/layout-templates/extract
```

默认 `mode=faithful`、`candidate_count=1`。MVP 在提取完成后自动把唯一安全候选创建为模板版本，因此当前前端无需立即重写。

建议新增可选字段：

```json
{
  "source_url": "https://mp.weixin.qq.com/s/...",
  "official_account_id": null,
  "name": "提取的新模板",
  "save_template": true,
  "mode": "faithful",
  "candidate_count": 1,
  "style_direction": null,
  "use_layout_profile": true
}
```

其中 `candidate_count` 在 `faithful` 模式必须为 1，在 `variations` 模式建议为 2—4，服务端设置硬上限。

### 12.2 真正异步化

截图和模型调用不应阻塞 API 请求。POST 返回 `202`、模板 ID、提取运行 ID 和状态。前端通过以下任一现有模式获取状态：

- 短期优先：继续轮询模板详情或模板列表中的 `extraction_status`；
- 后续增强：`GET /layout-template-extractions/{id}` 返回阶段、候选和错误；
- 如果复用全局 SSE Job 事件，则增加 `capturing`、`analyzing`、`generating_candidates`、`validating`、`rendering_preview`、`completed` 阶段。

### 12.3 多候选接口

进入 v2 后新增：

```http
GET  /api/v1/layout-template-extractions/{extraction_id}
POST /api/v1/layout-template-extractions/{extraction_id}/candidates/{candidate_id}/accept
```

接受候选是创建模板版本的唯一动作。接口校验运行和候选所有权，并使用幂等键防止重复创建版本。未接受候选不是正式模板版本，不得用于发布 Render。

## 13. 模型网关改造

### 13.1 能力要求

`layout_extraction` 路由引用的部署应至少满足：

- `vision` 或等价图片理解能力；
- `structured_output`；
- 足够的图片数量、图片尺寸和上下文窗口；
- 可配置的最大输出 Token 和超时；
- 可审计的请求 ID 和用量返回。

冻结路由时应校验能力列表，而不只是允许 `chat/vision` 模型类型。

### 13.2 统一多模态输入

现有 `ModelProvider.generate(purpose, prompt, context)` 可保持兼容，但新增内部请求对象或可选参数，用内容 Part 表达：

```text
ModelInputPart = TextPart | JsonPart | ImagePart
ImagePart      = private_object_key + mime_type + width + height + sha256
ModelOutput    = json_schema + strict
```

Provider 适配器负责把 `ImagePart` 转换为各供应商协议，不能把私有对象地址作为普通文本假设模型会自行访问。发送前由网关读取受限对象或生成极短期 URL；供应商不支持图片或强结构化输出时，该部署不能作为主路由。

### 13.3 提示词版本

新增并发布专用 Prompt Bundle，例如 `layout_extraction_agent`。提示词需要冻结：

- 角色和任务边界；
- 外部页面是不可信数据；
- 只允许引用配方目录；
- 不复制品牌素材和正文；
- 输出 Schema；
- 忠实模式与延展模式的差异；
- 缺少证据时降低置信度，不臆造复杂结构；
- 不输出 Markdown、HTML、CSS 代码或解释文本。

运行记录保存提示词版本 ID、变量哈希和输出校验值，不在普通日志保存完整截图、正文或蓝图上下文。

## 14. 确定性校验与编译

智能体输出至少经过以下门禁：

1. **JSON Schema 校验**：拒绝未知字段、缺失 ID、非法枚举和过深结构。
2. **StyleToken 校验**：复用并扩展现有 `validate_style_tokens()`。
3. **配方目录校验**：配方存在、适用于当前模块、参数在范围内。
4. **引用校验**：变体选择只引用当前模块已有变体，证据块存在。
5. **复杂度限制**：限制候选数、模块数、每模块变体数、嵌套层数和编译后节点数。
6. **内容独立性检查**：蓝图不得携带来源正文、任意外部图片 URL、账号二维码或 Logo。
7. **微信兼容编译**：只生成允许标签和内联样式，禁止脚本、事件、表单、iframe 和外链样式。
8. **几何检查**：375/414 宽度无横向溢出、图片不变形、长中文和 URL 可换行。
9. **可读性检查**：字号、行高、对比度和触发警戒的高饱和大面积背景。
10. **不可变版本检查**：蓝图、配方目录版本、文章版本和模板版本共同进入 Render 校验值。

模型只能建议修复，最终裁剪、替换和拒绝均由确定性代码执行。若校验器修改了模型结果，必须把修改项记录在候选质量信息中并降低置信度。

## 15. 视觉质量评测

### 15.1 忠实提取评分

对 `faithful` 模式，使用标准样例文章分别按来源观察和候选蓝图渲染，计算：

- 主色与背景色距离；
- 字号、字重、行高和间距误差；
- 标题、引用、重点段落等模块的结构覆盖率；
- 模块边界框和留白节奏差异；
- 截图视觉特征相似度；
- 人工标注评测集上的角色识别 F1。

视觉相似度只能用于排序，不能替代结构、安全和可读性门禁。

### 15.2 多样化评分

对 `variations` 模式同时检查：

- 每个候选与来源设计 DNA 的一致度；
- 候选之间的特征距离；
- 候选是否只进行了无意义的数值微调；
- 可读性和微信兼容性是否一致通过；
- Top-N 候选的用户选择率和后续编辑距离。

### 15.3 业务质量指标

建议将以下指标作为灰度放量门槛，而不是只看模型主观评分：

| 指标 | 建议门槛 |
|---|---:|
| 蓝图 Schema 首次通过率 | ≥ 98% |
| 一次受限修复后的合法率 | ≥ 99.5% |
| 危险 HTML/CSS 进入 Render | 0 |
| 375/414 视口非预期横向溢出 | 0 |
| 微信兼容编译通过率 | ≥ 99% |
| 人工评测的核心模块识别 F1 | ≥ 0.90 |
| 相对 DOM 基线的用户保存前编辑量 | 灰度期至少降低 30% |
| 多候选重复率 | ≤ 10% |
| 模型失败时错误归因和可见降级 | 100% |

这些是上线目标，不是对当前实现的测量结果。灰度前应先建立 DOM 基线数据，再决定最终阈值是否需要按业务样本调整。

## 16. 安全、版权与隐私

### 16.1 SSRF 与浏览器隔离

- 只允许 `https://mp.weixin.qq.com/s` 及确认需要支持的公开文章路径；
- 拒绝用户名、密码、非 443 端口和可疑编码；
- 首次解析及每次重定向均检查域名和解析后的 IP；
- 拒绝回环、私网、链路本地、保留地址和非预期协议；
- 限制响应大小、资源总量、重定向次数、渲染时间和截图像素；
- 浏览器使用无持久化上下文、低权限用户和容器沙箱；
- 不携带平台用户 Cookie，不允许页面访问内部服务或云元数据地址。

### 16.2 提示词注入

- 页面、截图 OCR、DOM 文本和外部图片都是数据，不是指令；
- 不把外部内容拼接到系统提示层；
- 智能体没有通用浏览器、Shell、数据库或发布工具；
- 输出只接受严格 Schema，未知字段直接拒绝；
- 任何页面文字都不能扩大配方目录和属性白名单。

### 16.3 版权边界

- 学习的是排版特征和抽象配方，不保存或复用来源正文；
- 不复制来源插画、摄影、Logo、二维码和独特品牌素材；
- 来源截图只用于提取和质量审计，设置可配置保留期；
- 训练数据进入离线集前移除 URL、账号标识、正文和可识别素材；
- 用户选择“忠实提取”时，前端应说明提取结果仍需用户确认其使用权。

### 16.4 数据控制

- 用户可以关闭“使用我的确认结果改进个人排版”；
- 默认只用于当前用户/公众号画像，不自动进入跨用户训练集；
- 跨用户训练需要单独的数据政策、授权和匿名化流程；
- 普通日志不记录网页正文、完整截图、模型完整上下文和用户文章；
- 删除用户、公众号或模板时执行画像、观察产物和反馈事件的关联清理。

## 17. 失败处理与回退

| 失败 | 处理 |
|---|---|
| 微信安全验证页或文章不可访问 | 明确失败，不生成模拟模板 |
| 浏览器渲染超时 | 可回退到已抓取 HTML 的基础观察；标记降级 |
| 截图失败但 DOM 可用 | 允许基础提取，不宣称多模态完成 |
| 模型路由不可用 | 使用有序备用部署；全部失败后可选基础提取 |
| 模型输出 Schema 非法 | 允许一次结构修复；仍失败则拒绝或基础提取 |
| 配方不兼容 | 确定性替换为同模块安全配方并降置信度，无法替换则拒绝候选 |
| 所有候选重复 | 返回较少候选并提示，不无限生成 |
| 视觉溢出或可读性失败 | 候选不可接受，不创建正式模板版本 |
| 用户在运行中删除模板 | Worker 再次检查事实状态并停止写入 |
| 重复任务消息 | 复用 Inbox/Job 去重，不重复创建模板版本 |

提取失败不得覆盖已有模板版本。已经创建的 Render 继续由其冻结版本保证不变；新模板版本只影响后续 Render。

## 18. 可观测性与成本控制

### 18.1 需要记录的指标

- 各阶段耗时：抓取、渲染、观察、模型分析、候选生成、校验和预览；
- 浏览器超时率、守卫页率、模型备用切换率和降级率；
- 输入截图数量、观察块数量、输入/输出 Token、调用成本；
- Schema 首次通过率、修复率、配方替换率、候选拒绝原因；
- 用户选择率、保存前字段差异、模板启用率、Render 确认率；
- 不同观察器、提示词、模型、Schema 和配方目录版本的质量对比。

### 18.2 成本约束

- 截图按视觉分段抽样，不把超长文章整图无上限发送给模型；
- 对相同 `source_content_hash + observer_version + prompt_version + profile_version + mode` 复用安全候选；
- 忠实模式默认一个候选，只有用户主动选择时才生成多候选；
- 候选预览使用固定样例文章，不调用模型生成正文；
- 结构修复最多一次；
- 对重复来源和重复账号画像使用对象哈希和结果缓存，但缓存不得跨用户泄露私有画像。

## 19. 测试方案

### 19.1 单元与契约测试

- URL、重定向、DNS 和私网地址校验；
- Layout Observation Schema 与节点/文本/图片上限；
- Blueprint v1/v2 Schema、未知字段和非法引用；
- 配方参数边界和 StyleToken 投影；
- 反馈事件去重和画像置信度更新；
- 旧 v1 模板与 Render 校验值兼容；
- 模型 Provider 的图片 Part、结构化输出和备用路由契约。

### 19.2 黄金样本集

建立版本化离线样本，每个样本包含：

- 脱敏 HTML fixture；
- 固定视口截图；
- 人工标注的模块角色和组合边界；
- 允许的排版蓝图或关键属性范围；
- 预期的安全失败/降级行为。

样本至少覆盖：纯文本、复杂 `section` 嵌套、数字标题、色块卡片、左右边框、居中标题、多级列表、长中文、超长 URL、图片说明、无内联样式、微信守卫页和恶意注入文本。

### 19.3 视觉和端到端测试

- 用固定文章结构生成候选预览并截图；
- 375、414、768 和桌面预览检查滚动与几何；
- 暗色管理界面不改变公众号正文 Render 的实际色值；
- 从链接提交、任务进度、候选选择、手工修改、保存模板到文章 Render 的完整流程；
- 模型失败、浏览器失败、重复消息和用户中途删除资源；
- 最终预览、公众号草稿和发布仍复用同一不可变 `render_id`。

## 20. 分阶段实施计划

### 阶段 0：建立基线和数据协议

目标：先知道现有规则在哪些版式上失败。

- 冻结 30—50 篇脱敏代表性文章作为初始黄金集；
- 为当前 DOM 提取器记录角色覆盖、StyleToken 误差和用户编辑量；
- 定义 `Layout Observation v1` 和智能体输出 v1 JSON Schema；
- 发布 `layout_extraction_agent` Prompt Bundle；
- 明确截图保留、删除和版权策略。

完成条件：黄金集可重复运行，现有基线可量化。

### 阶段 1：混合智能提取 MVP

目标：让现有入口真正调用排版智能体，同时不改前端模板数据结构。

- 将现有抓取器拆成“观察证据”和“DOM 基础候选”；
- 增加固定视口截图与受限计算样式；
- 扩展 Model Provider 支持图片 Part 和严格结构化输出；
- 在 `process_layout_extraction()` 中使用冻结的 `layout_extraction` 路由；
- 智能体输出当前 StyleToken v1、模块置信度和证据 ID；
- 复用 `validate_style_tokens()`、模板版本和现有编辑器；
- 模型失败时提供可见的基础提取降级；
- 将接口改为真实异步执行。

完成条件：黄金集核心模块 F1 和人工盲评优于 DOM 基线，安全与旧流程无回归。

### 阶段 2：Layout Blueprint v2 与多候选

目标：突破单一 StyleToken 的表达上限。

- 建立最小安全配方目录和确定性编译器；
- 新增蓝图、候选和提取运行数据模型；
- 前端增加“忠实提取/智能延展”和候选对比；
- 模板编辑器支持配方选择，但继续限制为受控选项；
- 增加候选去重、视觉评分和 v1 投影；
- Render 校验值包含蓝图和配方目录版本。

完成条件：多候选重复率、选择率和编辑量达到灰度门槛；旧 v1 模板全部兼容。

### 阶段 3：用户与公众号画像学习

目标：让系统随确认行为稳定贴近账号风格。

- 新增反馈事件和画像版本；
- 保存时计算智能候选到最终模板的字段级差异；
- 生成时检索同账号已确认范例和高置信度画像；
- 提供关闭、查看和重置排版学习能力；
- 进行 A/B 或 Shadow 评测，验证编辑量下降而非只提高模型自评。

完成条件：账号级模板的保存前编辑量持续下降，且不存在跨用户数据污染。

### 阶段 4：可选离线模型优化

目标：只有在运行时学习达到瓶颈后降低成本或提高识别质量。

- 建立脱敏、去重、版本化训练集；
- 训练候选模型并在冻结评测集对比；
- 先 Shadow，再小流量灰度；
- 任一安全、兼容、成本或用户指标退化即回滚模型路由。

此阶段不是前置依赖；前三阶段已经可以形成完整的“学习型排版智能体”。

## 22. 关键决策记录

### 决策 1：采用混合视觉智能体，不采用纯 DOM 或纯截图

纯 DOM 缺少视觉语义，纯截图缺少精确结构与数值。组合输入能同时获得视觉理解和确定性证据。

### 决策 2：模型输出蓝图，不输出 HTML

蓝图可校验、可编译、可版本化；任意 HTML/CSS 无法满足微信兼容、安全和历史 Render 可复现要求。

### 决策 3：首版不做在线微调

排版学习首先通过用户确认后的画像和范例检索完成。在线改权重难以撤销、易被噪声污染，也不利于用户隔离。

### 决策 4：先兼容 StyleToken v1，再引入 Blueprint v2

直接一次性替换数据模型、编辑器和渲染器风险过高。v1 MVP 可验证多模态识别是否真正创造价值，v2 再解决结构多样性。

### 决策 5：默认忠实提取，多样化由用户主动选择

链接提取的首要预期是接近参考文章。智能延展是独立模式，避免把“随机变化”误当成“智能提取”。

## 23. 最终推荐

建议立即进入阶段 0 和阶段 1，不要先训练新模型，也不要先建设复杂的多智能体系统。最短且正确的实现路径是：

1. 保留现有安全抓取和 DOM 提取器，把它改为观察证据与降级器；
2. 增加固定移动端截图和空间/计算样式清单；
3. 让现有 `layout_extraction` 模型路由真正调用一个多模态、强结构化输出的专用排版智能体；
4. 智能体首版仍输出现有 StyleToken，所有结果继续经过现有验证器和不可变模板版本；
5. 用黄金集和用户编辑量证明价值后，再实现 Blueprint v2、多候选和账号画像；
6. 只有画像检索已经不足、且拥有足够经确认的数据时，再考虑离线微调。

这条路线既能解决“只靠 HTML/DOM 不够智能”的核心问题，也不会牺牲当前系统已经建立的安全、微信兼容、可审计和不可变发布链路。
