# 微信公众号 AI 运营助手运维与恢复手册

## 1. 环境边界

开发、测试、预发布和生产必须使用不同的 PostgreSQL 实例/数据库、检索数据库、对象存储桶、RabbitMQ VHost、Redis 前缀、模型 Key 与微信第三方平台配置。禁止通过功能开关让非生产环境读取生产数据。

生产配置分为三类：公开配置、普通环境变量和 Secret。Secret 仅在运行时由 Secret Manager/KMS 或 Docker Secret 注入，不写入镜像、仓库、前端 bundle、日志或 Trace。

## 2. 部署与扩缩容

发布顺序固定为后端扩展兼容接口、数据库向前兼容迁移、两个前端升级、数据回填与核验、切换默认、后续版本再清理旧契约。数据库迁移遵循“扩展—回填—切换—清理”，不得在同一发布中直接删除仍被旧应用读取的字段。

API 无状态水平扩展；AI、解析、Embedding、微信和同步 Worker 按各自队列积压、供应商 RPM/TPM、CPU/GPU 和错误率独立扩展。Scheduler 只运行一个逻辑实例，并使用数据库顾问锁或短期 Redis 锁防止重复调度；锁不能代替业务状态。

### 2.1 生产构建边界

生产服务器只负责导入或拉取版本化镜像、执行数据库迁移和切换容器，不负责安装依赖或编译应用。禁止在生产服务器执行以下命令：

```text
pnpm install
pnpm build
docker compose build user-web
docker compose build admin-web
uv sync
pip install
docker compose build backend-api
```

前端和后端都必须先在本地工作站或 CI 完成生产构建。当前通过 SSH 交付时，以完整 Docker 镜像作为构建产物，不直接覆盖 Nginx 的 `dist` 目录或服务器源码。最终前端运行镜像只包含 Nginx、静态资源和健康检查，不包含 Node.js、`node_modules`、测试工具或移动端构建工具；最终后端镜像已经包含锁定的生产 Python 环境，生产服务器不再运行 `uv sync`。

Git 管理源码、Dockerfile、Compose、Alembic 和本手册；镜像归档通过 SSH 或镜像仓库传输。禁止把 `dist`、Docker 镜像归档、真实 `.env`、密钥或生产数据库内容提交到 Git。

### 2.2 发布版本与平台

1. 完成本次范围内的测试和生产构建检查。
2. 提交并推送目标分支，记录完整 Git SHA 和短 SHA。
3. 发布标签固定为 `git-<short-sha>`，不得使用会漂移的 `latest`。
4. 本地构建必须指定与生产服务器一致的平台；当前 Linux AMD64 服务器使用 `--platform linux/amd64`。
5. 正式目标使用 `USER_WEB_VERSION`、`ADMIN_WEB_VERSION` 和 `BACKEND_VERSION` 独立控制服务版本，Worker 与 Scheduler 跟随 `BACKEND_VERSION`。当前 Compose 尚未完成拆分，过渡期仍使用共享 `APP_VERSION`；切换前必须确保该标签下的全部所需镜像都已存在于服务器。

示例：

```powershell
$releaseSha = (git rev-parse --short HEAD).Trim()
if ($LASTEXITCODE -ne 0) { throw "无法读取 Git 版本" }
$releaseTag = "git-$releaseSha"

docker build --platform linux/amd64 --target production `
  --tag "wechat-ai-user:$releaseTag" `
  apps/user-client

docker build --platform linux/amd64 --target production `
  --tag "wechat-ai-admin:$releaseTag" `
  apps/admin-console

docker build --platform linux/amd64 --target runtime `
  --tag "wechat-ai-backend:$releaseTag" `
  services/platform-backend
```

完成独立版本变量拆分后，只构建、上传和重启实际变更的服务。过渡期共享 `APP_VERSION` 切换前仍须确保其余服务的新标签镜像存在。不得为了省略这个检查而让生产服务器临时构建缺失镜像。

### 2.3 导出、校验与 SSH 传输

镜像按发布版本导出到本机临时目录，生成 SHA-256 清单，再通过 SSH 传输。归档文件不得放进仓库工作区。

```powershell
$artifactRoot = Join-Path $env:TEMP "wechat-operation-$releaseTag"
New-Item -ItemType Directory -Force -Path $artifactRoot | Out-Null

$userArchive = Join-Path $artifactRoot "wechat-ai-user-$releaseTag.tar"
$adminArchive = Join-Path $artifactRoot "wechat-ai-admin-$releaseTag.tar"
$backendArchive = Join-Path $artifactRoot "wechat-ai-backend-$releaseTag.tar"

docker save --output $userArchive "wechat-ai-user:$releaseTag"
docker save --output $adminArchive "wechat-ai-admin:$releaseTag"
docker save --output $backendArchive "wechat-ai-backend:$releaseTag"

Get-FileHash $userArchive, $adminArchive, $backendArchive -Algorithm SHA256
```

上传时使用操作者自己的 SSH 主机别名或密钥配置，不把私钥路径、口令或服务器 Secret 写进仓库：

```powershell
scp $userArchive $adminArchive $backendArchive <production-host>:/opt/wechat-operation/.deploy-images/
```

服务器导入前后都要核对文件大小和 SHA-256；导入完成后确认镜像标签及目标架构：

```bash
cd /opt/wechat-operation
RELEASE_VERSION=git-<short-sha>
sha256sum .deploy-images/*-${RELEASE_VERSION}.tar
docker load --input .deploy-images/wechat-ai-user-${RELEASE_VERSION}.tar
docker load --input .deploy-images/wechat-ai-admin-${RELEASE_VERSION}.tar
docker load --input .deploy-images/wechat-ai-backend-${RELEASE_VERSION}.tar
docker image inspect \
  wechat-ai-user:${RELEASE_VERSION} \
  wechat-ai-admin:${RELEASE_VERSION} \
  wechat-ai-backend:${RELEASE_VERSION}
```

文件名可以按实际传输方式调整，但镜像内部标签必须与目标 Git SHA 一致。导入失败或校验不一致时停止发布，不更新 `APP_VERSION`。

### 2.4 生产切换

1. 确认生产工作区没有未知修改；如有修改，先停止发布并审计来源，不能直接覆盖。
2. 使用 `git fetch` 和 `git merge --ff-only` 将生产工作区更新到已推送的目标提交。
3. 确认 `git rev-parse HEAD` 与构建镜像所用提交完全一致。
4. 记录当前 `APP_VERSION` 作为回滚版本。
5. 备份受迁移影响的数据或结构，并先运行版本化后端镜像中的 Alembic 迁移。
6. 确认所有目标镜像已经导入后，才更新 `.env.server` 中的 `APP_VERSION`。
7. 使用 `--no-build` 重建服务，再重启网关，禁止任何隐式构建。

```bash
git fetch origin main
git merge --ff-only origin/main
git status --short
git rev-parse --short HEAD

APP_VERSION=${RELEASE_VERSION} docker compose --env-file .env.server \
  -f deploy/compose/compose.server-preview.yml \
  config --images

APP_VERSION=${RELEASE_VERSION} docker compose --env-file .env.server \
  -f deploy/compose/compose.server-preview.yml \
  run --rm --no-deps backend-api uv run alembic upgrade head

docker compose --env-file .env.server \
  -f deploy/compose/compose.server-preview.yml \
  up -d --no-build --force-recreate \
  user-web admin-web backend-api worker scheduler

docker compose --env-file .env.server \
  -f deploy/compose/compose.server-preview.yml \
  restart gateway
```

不得使用普通 `git merge` 制造生产专属合并提交，不得在生产服务器提交源码，不得用 `scp` 直接覆盖已检出的源码文件。

### 2.5 发布验证与回滚

发布完成必须核对：

- 生产 Git HEAD、`APP_VERSION` 和每个运行容器镜像标签一致。
- API liveness、readiness 和前端健康检查成功。
- 最近容器日志没有迁移错误、Traceback、持续 5xx 或数据库截断错误。
- 本次变更对应的关键路径通过真实域名烟雾测试。
- 前端页面没有加载旧哈希资源或混合版本资源。

验证失败时停止继续变更，恢复上一个 `APP_VERSION`，并使用已保留的旧镜像执行：

```bash
docker compose --env-file .env.server \
  -f deploy/compose/compose.server-preview.yml \
  up -d --no-build --force-recreate \
  user-web admin-web backend-api worker scheduler

docker compose --env-file .env.server \
  -f deploy/compose/compose.server-preview.yml \
  restart gateway
```

数据库回滚必须遵循对应迁移的恢复方案。除非已经验证数据兼容性和备份，否则不能仅因应用回滚就自动执行 Alembic downgrade。

### 2.6 后端低资源发布细则

后端发布与前端遵循同一个原则：生产服务器只运行成品。标准流程为：

```text
本地或 CI 执行 Ruff、mypy、pytest 和 Alembic 空库升级
→ 构建 linux/amd64 runtime 镜像
→ 使用 Git SHA 标记镜像
→ 本地启动镜像并检查 Alembic head 与应用导入
→ 通过 SSH 上传或推送镜像仓库
→ 生产服务器 docker load 或 docker pull
→ 使用目标后端镜像单独执行迁移
→ 使用 --no-build 切换 API、Worker 和 Scheduler
```

后端生产镜像必须在本地或 CI 构建：

```powershell
docker build --platform linux/amd64 --target runtime `
  --tag "wechat-ai-backend:$releaseTag" `
  services/platform-backend

docker run --rm "wechat-ai-backend:$releaseTag" `
  uv run python -c "from app.main import app; print(app.title)"

docker run --rm "wechat-ai-backend:$releaseTag" `
  uv run alembic heads
```

生产数据库不能打包覆盖，也不能提交到 Git。Git 只保存 Alembic 迁移；发布时从目标后端镜像显式执行：

```bash
BACKEND_VERSION=git-<short-sha>

APP_VERSION=${BACKEND_VERSION} docker compose --env-file .env.server \
  -f deploy/compose/compose.server-preview.yml \
  run --rm --no-deps backend-api uv run alembic upgrade head

APP_VERSION=${BACKEND_VERSION} docker compose --env-file .env.server \
  -f deploy/compose/compose.server-preview.yml \
  run --rm --no-deps backend-api uv run python scripts/migrate_retrieval.py
```

以上 `APP_VERSION=${BACKEND_VERSION}` 是共享版本变量过渡期写法。版本变量拆分完成后必须直接使用 `BACKEND_VERSION`，不再改动或重启两个前端。

当前生产 Compose 的 API 启动命令仍包含 Alembic 和检索迁移，这是遗留安全网，不是正式发布步骤。正式发布必须先显式执行迁移并确认成功，使 API 启动时只得到无变更结果；后续 Compose 改造应将迁移拆成一次性 `migrate` 服务，并让 `backend-api` 命令只启动 Uvicorn。Worker 和 Scheduler 不得先于迁移成功切换。

### 2.7 独立服务版本与最小重启

Compose 应拆分为三个版本变量：

```text
USER_WEB_VERSION=git-<user-sha>
ADMIN_WEB_VERSION=git-<admin-sha>
BACKEND_VERSION=git-<backend-sha>
```

镜像映射固定为：

```yaml
user-web:
  image: wechat-ai-user:${USER_WEB_VERSION}

admin-web:
  image: wechat-ai-admin:${ADMIN_WEB_VERSION}

backend-api:
  image: wechat-ai-backend:${BACKEND_VERSION}

worker:
  image: wechat-ai-backend:${BACKEND_VERSION}

scheduler:
  image: wechat-ai-backend:${BACKEND_VERSION}
```

发布范围遵循最小重启原则：

- 只改用户端：构建、上传并重启 `user-web`；网关、后端和管理端保持运行。
- 只改管理端：构建、上传并重启 `admin-web`；网关、用户端和后端保持运行。
- 只改后端且没有迁移：构建、上传并重启 `backend-api`、`worker`、`scheduler`；两个前端保持原版本。
- 后端包含迁移：先备份和显式迁移，再按依赖顺序切换后端服务。
- 只改文档或测试且不影响镜像构建上下文：不构建、不上传、不重启任何生产容器。

独立变量切换示例：

```bash
docker compose --env-file .env.server \
  -f deploy/compose/compose.server-preview.yml \
  up -d --no-build --force-recreate backend-api worker scheduler
```

任何时候都不得使用无服务名的 `docker compose up -d --force-recreate` 全量重启。只切换本次变更需要的服务，并保留各服务上一版本镜像标签用于独立回滚。

## 3. 备份

业务数据库和检索数据库至少每日备份，业务库启用持续归档/PITR。对象存储开启版本控制、跨区域复制或等价备份，原始文件不能仅依赖数据库记录。密钥管理、微信平台配置、RabbitMQ 定义与监控告警规则同样需要版本化备份。

本地数据库备份：

```powershell
node scripts/backup-databases.mjs
node scripts/verify-backup.mjs backups/<timestamp>
```

脚本只生成两个 PostgreSQL 自定义格式 dump 和 SHA-256 清单，不会把对象存储伪装成已备份。生产对象存储必须使用云厂商/存储平台的版本、复制与恢复能力单独核验。

## 4. 恢复演练

恢复必须先在隔离环境进行，禁止直接覆盖生产。演练步骤：

1. 创建空业务库、空检索库和独立对象存储桶。
2. 使用 `pg_restore --clean --if-exists --no-owner` 恢复数据库备份。
3. 恢复对象存储并核对原文件哈希、派生物可重建标记和私有访问策略。
4. 运行 Alembic 升级到目标应用版本。
5. 执行用户隔离、文章版本、文章库列表、Render 校验值与微信操作状态核对。
6. 对检索库执行抽样回源；必要时从业务事实和对象存储重建块、全文索引和向量。
7. 记录 RPO、RTO、失败点和改进项。正式上线前以及重大数据库变更后必须完成演练。

## 5. 故障处理

- 模型 429：遵守 `Retry-After`，按路由有限重试后切换已发布备用模型；不重复结算额度。
- 模型鉴权失败：停用部署并告警，不继续用同一凭据重试。
- 文件扫描/解析失败：保留隔离对象和阶段检查点；失败内容不进入 AI 上下文。
- 检索服务失败：降级为权限过滤后的全文检索；权限过滤永不降级。
- 微信 `UNKNOWN`：先按外部 ID 查询或等回调对账，禁止直接重放。
- 草稿已创建但发布失败：复用原 `media_id`，不得再次创建草稿。
- SSE 断开：后台任务继续；客户端携带 `Last-Event-ID` 补发，不重新创建运行或扣额度。

## 6. 监控与告警

最低告警集包括 API 5xx/延迟、认证异常、模型失败率与费用、队列积压/死信、文件扫描与解析失败、Embedding 积压、微信令牌刷新/草稿/发布失败、数据库连接/磁盘/复制延迟、对象存储错误和备份失败。Trace、Metric 与 Log 使用同一请求/运行 ID 关联，同时删除 Authorization、Cookie、完整手机号、用户正文、文件全文和所有 Secret。

## 7. 上线门禁

上线前必须具备正式 HTTPS 域名、企业与备案材料、主/备模型和预算、微信第三方平台与测试/正式公众号、生产对象存储、短信、监控告警、用户协议/隐私政策/版权与 AI 内容说明，以及目标平台的签名和商店账号。缺少任一外部账号时，相应 Provider 只能保持 Mock/disabled，不能把模拟结果报告为生产联调成功。
