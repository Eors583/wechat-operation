# 微信公众号 AI 运营助手运维与恢复手册

## 1. 环境边界

开发、测试、预发布和生产必须使用不同的 PostgreSQL 实例/数据库、检索数据库、对象存储桶、RabbitMQ VHost、Redis 前缀、模型 Key 与微信第三方平台配置。禁止通过功能开关让非生产环境读取生产数据。

生产配置分为三类：公开配置、普通环境变量和 Secret。Secret 仅在运行时由 Secret Manager/KMS 或 Docker Secret 注入，不写入镜像、仓库、前端 bundle、日志或 Trace。

## 2. 部署与扩缩容

默认上线模式为 **GitHub Actions 构建并上传镜像 → GitHub 通过 SSH 自动操作服务器 → 服务器拉取镜像并切换服务**。本节替代原来的本机 Docker 构建、手动导出与上传镜像流程；日常上线不依赖本机 Docker。

API 无状态水平扩展；Worker 按队列积压、供应商限流和资源占用独立扩展。Scheduler 只运行一个逻辑实例，并以数据库顾问锁或短期 Redis 锁防止重复调度。

### 2.1 发布入口与构建边界

1. 将本次变更单独提交并推送到 GitHub `main`，不要包含无关工作区修改。
2. 打开 [Production release 工作流](https://github.com/Eors583/wechat-operation/actions/workflows/production-release.yml)，点击 **Run workflow**。
3. 分支选择 `main`，服务选择 `backend`、`user` 或 `admin`，启动发布。
4. GitHub 自动执行脚本 ShellCheck、对应项目 lint、生产镜像构建、GHCR 推送、源码交付、镜像拉取和服务切换。
5. 查看该次运行的结果和服务器发布日志，记录版本与交付方式，再交给用户手动验收。

目前为手动触发工作流，选定服务后自动完成发布，普通 Git push 不触发生产上线。每次只发布一个服务；多个服务需要分别启动，优先发布向前兼容的后端，再发布依赖它的前端。同服务工作流串行，服务器共享发布锁串行处理容器切换。若较新提交已上线，旧提交发布会被拒绝，应从包含所需修改的最新 `main` 重新发布。

GitHub 托管 Ubuntu runner 负责构建 `linux/amd64` 镜像。本机负责编辑、提交和触发；生产服务器只负责成品镜像接收、显式迁移与容器运行，禁止执行应用依赖安装、前端编译或 `docker compose build`，包括 `pnpm install`、`pnpm build`、`uv sync`、`pip install`。

日常发布只运行相关 lint 和必要生产构建，不自动运行测试。后端 lint 为 `uv run --project services/platform-backend --frozen ruff check services/platform-backend`；前端为 `pnpm --dir apps/user-client lint` 或 `pnpm --dir apps/admin-console lint`。不要用包含测试的 `suite-ci` 替代发布工作流；提交消息中的 `[skip ci]` 不影响手动触发 Production release。只有用户明确要求测试时，才执行测试或生产冒烟验证。

### 2.2 镜像、版本与发布范围

镜像标签固定为 `git-<构建提交的7位SHA>`，OCI revision 标签保存完整 SHA，拉取以构建返回的 SHA-256 digest 为准，不使用 `latest`。

| 工作流 service | 完整镜像仓库 | 仓库变量 / 版本变量 | 切换服务 |
| --- | --- | --- | --- |
| `backend` | `ghcr.io/eors583/wechat-ai-backend` | `BACKEND_IMAGE_REPOSITORY` / `BACKEND_VERSION` | `backend-api`、`worker`、`scheduler` |
| `user` | `ghcr.io/eors583/wechat-ai-user` | `USER_WEB_IMAGE_REPOSITORY` / `USER_WEB_VERSION` | `user-web` |
| `admin` | `ghcr.io/eors583/wechat-ai-admin` | `ADMIN_WEB_IMAGE_REPOSITORY` / `ADMIN_WEB_VERSION` | `admin-web` |

版本持久化在生产 `.env.server`。只构建、更新和重建受影响服务，随后重启网关；禁止省略服务名后全量强制重建。其他服务允许继续运行自己的历史 Git 版本，生产 HEAD 必须包含这些版本对应的提交。文档改动无需构建镜像或重启容器。

Git 是源码事实来源。工作流从已推送的构建提交生成 Git bundle，通过 SSH 交付，生产 checkout 只允许快进到该提交。生产工作区有修改、目标提交更旧或分叉时停止，不能覆盖未知修改或创建生产专属合并提交。禁止提交 `dist`、镜像归档、真实环境文件、密钥或生产数据库。

### 2.3 凭据与服务器入口

GitHub `production` Environment 只允许 `main` 部署，配置：

| 类型 | 名称 | 用途 |
| --- | --- | --- |
| Secret | `PRODUCTION_SSH_KEY` | 专用 Ed25519 部署私钥 |
| Secret | `PRODUCTION_KNOWN_HOSTS` | 经管理员核对的服务器 SSH 主机公钥记录 |
| Variable | `PRODUCTION_HOST` | 生产主机地址 |

构建 job 使用内置 `GITHUB_TOKEN` 的代码读取和包写入权限；部署 job 使用独立临时令牌，仅有代码读取和包读取权限。通过加密 SSH 标准输入传入服务器，再以 `docker login --password-stdin` 登录。Docker 登录配置放在临时目录并在退出时删除，不写入 `.env.server`、仓库或日志。日常发布无需本机 Docker 登录或长期个人 Registry Token。

服务器运行目录为 `/opt/wechat-operation`，使用 `.env.server` 与 `deploy/compose/compose.server-preview.yml`。管理员首次安装，或更新这两个脚本后，从已审核并推送的 Git 版本重新安装：

```bash
cd /opt/wechat-operation
install -d -m 700 /usr/local/lib/wechat-ci
install -m 700 scripts/ci-ssh-entry.sh /usr/local/sbin/wechat-ci-entry
install -m 700 scripts/deploy-ci-release.sh /usr/local/lib/wechat-ci/deploy-ci-release.sh
```

专用公钥在 root 的 `authorized_keys` 使用以下限制前缀：

```text
restrict,command="/usr/local/sbin/wechat-ci-entry" ssh-ed25519 <专用公钥>
```

入口仅允许经参数校验的 `stage`、`archive`、`deploy` 操作，不提供交互 shell 或转发。两个脚本固定安装在仓库外，仅快进仓库不会更新已安装入口。不要上传个人日常 SSH 私钥。

### 2.4 镜像交付与切换

自动发布按以下顺序执行：

1. 获取服务器发布锁，检查工作区、目标提交、上一版镜像及数据库迁移差异。
2. 服务器按 digest 从 GHCR 拉取镜像，校验 Linux AMD64 平台和完整 Git revision。
3. GHCR 登录超过 45 秒或拉取超过 180 秒等失败返回指定状态码时，工作流自动改由 GitHub runner 下载同一 digest 的镜像、压缩并经 SSH 上传。校验归档 SHA-256、镜像配置摘要、文件层、平台和 revision 后导入。回退仍由 GitHub 提供成品，不需要本机或服务器构建。
4. 将旧仓库、旧版本和镜像 ID，以及目标引用、digest、交付方式写入 `.deploy-images/ci-<service>-git-<sha>-rollback.txt`。
5. 快进生产 Git，原子更新 `.env.server` 中本服务的仓库和版本，再以 `docker compose up -d --no-build --no-deps --force-recreate <受影响服务>` 切换，随后重启网关。
6. 输出容器状态和实际交付方式，并按 2.8 清理旧产物。

发布日志中的 `Delivery: registry` 表示服务器直接拉取，`Delivery: github-ssh-archive` 表示 GitHub SSH 归档回退；交付方式同时存入回滚记录。镜像校验失败不得更新版本。当前仓库和版本已与目标一致时，脚本确认目标容器运行相同镜像后直接结束，保留原回滚记录和上一版镜像。

### 2.5 失败处理与回滚

lint、构建、交付或切换前校验失败时，停止并处理该阶段错误。容器切换或网关重启命令失败时，部署脚本尝试恢复受影响服务原仓库和版本并重建；必须查看回滚命令结果，不能仅凭工作流结束断言恢复成功。清理阶段失败可能发生在容器已经切换之后，应先核对运行版本再处理，不要盲目重复发布。

功能验收失败时，管理员读取对应回滚记录，将记录中的仓库变量和版本变量一起恢复到 `.env.server`，确认旧镜像仍存在，再仅重建需要回滚的服务。例如后端：

```bash
cd /opt/wechat-operation
# 先根据回滚记录恢复 .env.server 中的 BACKEND_IMAGE_REPOSITORY 和 BACKEND_VERSION。
docker compose --env-file .env.server -f deploy/compose/compose.server-preview.yml \
  up -d --no-build --no-deps --force-recreate backend-api worker scheduler
docker compose --env-file .env.server -f deploy/compose/compose.server-preview.yml restart gateway
```

前端分别恢复自己的仓库、版本，并将服务名替换为 `user-web` 或 `admin-web`。不要通过向旧提交重跑普通发布工作流来回滚，因为工作流只接受 Git 快进。应用回滚不自动回退数据库；Alembic downgrade 需要单独评估兼容性和恢复方案。

工作流成功表示 lint、构建、交付和服务切换完成，不等于业务功能通过。交付说明应包含工作流链接、服务、Git 版本、交付方式、回滚版本和“功能未验证”。功能由用户手动验收；只有用户明确要求测试后，代理才执行健康接口、日志审查及关键路径冒烟测试。

### 2.6 后端快速增量上线细则

普通后端更新以本节为默认入口：

1. 完成修改，单独提交并推送到 `main`。
2. 运行 **Production release**，选择 `main` 和 `backend`。
3. 等待 GitHub 完成 Ruff、镜像构建、GHCR 推送及自动部署；无需启动本机 Docker 或执行 `publish-backend-image.ps1`。
4. 确认该次工作流结果、实际交付方式与回滚记录。仅切换 API、Worker、Scheduler，并重启网关。
5. 将新版本交给用户手动验收；未获测试指令时注明功能未验证。

层缓存和 Registry 会复用未变化的镜像层；实际耗时以工作流记录为准。用户端和管理端使用同一入口，各自选择 `user`、`admin`，独立上线。

### 2.7 数据库迁移例外

数据库变更必须提交 Alembic migration，遵循“扩展—回填—切换—清理”，先完成兼容性迁移，再切换依赖它的应用；不得在同一发布直接删除旧应用仍读取的字段。

当前自动部署脚本比较上一后端版本与目标提交的 `services/platform-backend/migrations`。文件有差异就停止，**没有“已迁移”标记或自动放行机制；手动迁移后直接重跑仍会停止**。这类版本由管理员按以下受控流程完成，不能绕过差异检查假装普通发布成功：

1. 从该次 GitHub 构建记录确定完整提交、镜像仓库、标签和 digest；备份受影响数据与结构，记录当前后端完整引用及镜像 ID。
2. 通过 Registry 或经校验的 GitHub 归档准备同一目标镜像；确保生产 Git 干净并快进到目标提交，校验镜像平台与 revision。
3. 从目标镜像显式执行一次迁移，失败立即停止。以下占位值需替换为该次真实镜像：

```bash
BACKEND_IMAGE_REPOSITORY=ghcr.io/eors583/wechat-ai-backend \
BACKEND_VERSION=git-<目标7位SHA> \
docker compose --env-file .env.server -f deploy/compose/compose.server-preview.yml \
  run --rm --no-deps backend-api /opt/venv/bin/python -m alembic upgrade head
```

4. 涉及检索库时，按该变更的迁移说明，从同一目标镜像单独执行对应迁移命令。生产数据库内容不得打包覆盖或进入 Git。
5. 迁移成功后才持久化目标仓库、版本，按 2.4 的 `--no-build --no-deps` 命令切换后端，再按 2.8 清理和记录。保留恢复所需备份；功能测试仍须用户明确要求。

当前生产 API 命令只启动 Uvicorn，不执行启动迁移。不得依赖 API、Worker 或 Scheduler 启动完成迁移。

### 2.8 发布镜像清理

构建在 GitHub runner 完成，生产服务器不产生应用构建缓存。服务器会保存运行镜像、回滚镜像和临时交付包，采用两层清理：每次成功发布清理旧镜像，每日清理中断发布遗留的临时文件。

服务器 cron 按服务器时区每天 04:30 执行 `scripts/cleanup-release-temp.sh`，只删除 `.deploy-images` 顶层超过 7 天的 CI bundle、CI 上传临时文件以及三个应用的镜像归档和旁文件；保留回滚记录，不删除 Docker 镜像、容器、卷或业务数据。发布锁被占用时跳过当次清理。管理员从已提交的版本安装：

```bash
install -m 700 scripts/cleanup-release-temp.sh /usr/local/lib/wechat-ci/cleanup-release-temp.sh
install -m 644 deploy/wechat-release-cleanup.cron /etc/cron.d/wechat-release-cleanup
```

清理记录进入系统日志，标记为 `wechat-release-cleanup`。更新脚本或计划后需要重新安装。GitHub runner 构建缓存和 GHCR 远端镜像不占生产磁盘，不属于此服务器任务的清理范围。

自动发布在成功切换后调用 `scripts/prune-release-images.sh`，按服务保留当前和紧邻上一版本。管理员处理迁移发布或补做清理时，从真实发布记录取得当前、上一标签和仓库，仅对本次变更服务执行，例如：

```bash
bash scripts/prune-release-images.sh backend git-<current-sha> git-<previous-sha> ghcr.io/eors583/wechat-ai-backend
```

前端分别使用 `user` / `ghcr.io/eors583/wechat-ai-user`、`admin` / `ghcr.io/eors583/wechat-ai-admin`。两个版本相同会跳过清理；不得把重复发布的当前版本当成真正上一版本。

首次从旧仓库切换 GHCR 时，保留原完整引用，并为上一版建立新仓库的本地标签供清理脚本保留。旧仓库原镜像继续作为回滚保障，不随新仓库清理删除。

清理范围为指定仓库其他 `git-*` 镜像标签与该服务旧归档，不处理远端 GHCR、其他仓库、数据库或持久卷。已使用的 CI 压缩归档与校验旁文件在成功发布后删除，Docker 内保留当前和上一镜像。旧镜像被容器引用时先核对来源，不强制删除。


## 3. 备份

业务数据库和检索数据库至少每日备份，业务库启用持续归档/PITR。对象存储开启版本控制、跨区域复制或等价备份，原始文件不能仅依赖数据库记录。密钥管理、微信平台配置、RabbitMQ 定义与监控告警规则同样需要版本化备份。

本地数据库备份：

```powershell
node scripts/backup-databases.mjs
node scripts/verify-backup.mjs backups/<timestamp>
```

脚本只生成两个 PostgreSQL 自定义格式 dump 和 SHA-256 清单，不会把对象存储伪装成已备份。生产对象存储必须使用云厂商/存储平台的版本、复制与恢复能力单独核验。

## 4. 恢复演练

恢复必须先在隔离环境进行，禁止直接覆盖生产。演练步骤：

1. 创建空业务库、空检索库和独立对象存储桶。
2. 使用 `pg_restore --clean --if-exists --no-owner` 恢复数据库备份。
3. 恢复对象存储并核对原文件哈希、派生物可重建标记和私有访问策略。
4. 运行 Alembic 升级到目标应用版本。
5. 执行用户隔离、文章版本、文章库列表、Render 校验值与微信操作状态核对。
6. 对检索库执行抽样回源；必要时从业务事实和对象存储重建块、全文索引和向量。
7. 记录 RPO、RTO、失败点和改进项。正式上线前以及重大数据库变更后必须完成演练。

## 5. 故障处理

- 模型 429：遵守 `Retry-After`，按路由有限重试后切换已发布备用模型；不重复结算额度。
- 模型鉴权失败：停用部署并告警，不继续用同一凭据重试。
- 文件扫描/解析失败：保留隔离对象和阶段检查点；失败内容不进入 AI 上下文。
- 检索服务失败：降级为权限过滤后的全文检索；权限过滤永不降级。
- 微信 `UNKNOWN`：先按外部 ID 查询或等回调对账，禁止直接重放。
- 草稿已创建但发布失败：复用原 `media_id`，不得再次创建草稿。
- SSE 断开：后台任务继续；客户端携带 `Last-Event-ID` 补发，不重新创建运行或扣额度。

## 6. 监控与告警

最低告警集包括 API 5xx/延迟、认证异常、模型失败率与费用、队列积压/死信、文件扫描与解析失败、Embedding 积压、微信令牌刷新/草稿/发布失败、数据库连接/磁盘/复制延迟、对象存储错误和备份失败。Trace、Metric 与 Log 使用同一请求/运行 ID 关联，同时删除 Authorization、Cookie、完整手机号、用户正文、文件全文和所有 Secret。

## 7. 上线门禁

上线前必须具备正式 HTTPS 域名、企业与备案材料、主/备模型和预算、微信第三方平台与测试/正式公众号、生产对象存储、短信、监控告警、用户协议/隐私政策/版权与 AI 内容说明，以及目标平台的签名和商店账号。缺少任一外部账号时，相应 Provider 只能保持 Mock/disabled，不能把模拟结果报告为生产联调成功。
