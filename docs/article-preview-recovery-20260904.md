# 文章 JSON 正文与历史预览串版本修复

## 已核实的两个根因

1. 模型输出存在提前闭合、缺失对象括号等 JSON 语法错误。供应商适配器回退为普通段落，原有文章验证仅验证外层 Tiptap 节点，错误正文因此被保存。
2. CreatePage 的所有聊天文章卡片都使用任务当前 article 展示并调用 openArticle(article)，没有使用各消息的 article_id/version_no。旧消息的预览因此也显示最新的损坏版本。不是模型修改了其他文章。

数据库检查时共有 5 篇文章，只有文章 01a06a13-df3a-7d1b-bdda-c9fb643a64c5 的当前第 4 版为序列化 JSON 正文；该文章第 2、3 版正常结构仍在。其他文章没有此类 JSON 正文，但此前抓取失败说明、文件完成说明等旧内容质量问题不属于本次已恢复范围。

## 修复

- 生成结果保存前识别完整文档重复编码，有限层数解码并执行 canonical 校验。
- 损坏的文档 JSON 不再被当作普通文章通过。进入既有一次结构修复流程；修复仍失败则不创建文章版本。
- 生成文章的助手文本来自规范化后的文档，避免流式显示 JSON；新文章标题优先取首个 H1，不再取用户 URL 请求。
- 消息映射保留 version_no。预览根据消息的 article_id/version_no 获取对应版本，支持版本分页；不存在时明确失败，不回退最新版。
- 历史版本只读，隐藏保存/发布操作；卡片不再借用当前文章的标题和摘要。

## 数据恢复

专项脚本 services/platform-backend/scripts/repair_serialized_article_v4.py 默认 dry-run，只针对已确认的第 4 版。
修复 3 处缺失对象起始符并读取所有后续节点，校验 75 个 text 节点顺序和值完全一致。
当前编辑器不支持的 table 按原行/单元格顺序转换为列表段落，正文文字未重新生成。
调用已有版本服务，使用 base_version_no=4 乐观并发校验创建第 5 版，保留所有旧版，失效旧渲染缓存。
另追加一条明确标注恢复的助手消息，关联第 5 版；不改写之前消息的历史关联。

## 验收

- 后端新增重复编码、代码围栏、提前闭合、截断、正常代码示例，以及一次修复成功/失败不落库测试。
- 前端新增消息文章 ID/版本隔离、分页、缺失版本不可替换、当前版本可编辑测试。
- 浏览器脚本 apps/user-client/scripts/check-message-preview.mjs 拦截所有 API，仅使用测试数据，不触发真实生成/写入。
- 验证 1440×900、1280×720、1024×768、390×844 的 light/dark：A 历史 v2 与 B 当前 v1 切换、只读/可编辑隔离；各尺寸 root scrollWidth 等于 clientWidth。
- 截图 artifacts/message-preview-{width}-{theme}.png。
- Docker PostgreSQL 未切换；API 与空闲 AI Worker 已重新加载修复代码。

原第 4 版作为故障历史仍保留，需看恢复稿时使用第 5 版入口。模型仍可能返回错误，修复的保证是该类错误不能再冒充成功文章保存，以及历史入口不再串到其他版本；并非保证模型永远不出错。
